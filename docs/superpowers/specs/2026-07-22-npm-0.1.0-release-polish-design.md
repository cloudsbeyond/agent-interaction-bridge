# npm 0.1.0 Release Polish Design

> Scope update (2026-07-22): the three product fixes remain in scope, but npm
> package and publication readiness are deferred until the broader feature set
> is complete. This iteration ends at a clean, locally verified PR-ready branch.

## Objective

Complete three bounded operator-experience fixes and prepare them for code
review:

1. `service start/restart launchd` waits for a connected bridge runtime before
   reporting success.
2. A task approval card becomes non-interactive as soon as its decision is
   accepted.
3. A single Feishu/Lark slash command wrapped as a fenced plain-text block is
   normalized back into a command.

No npm registry, identity, tarball, install, or publication checks run in this
iteration. Those release actions remain human-owned and explicitly deferred.

## Design

### 1. Condition-driven LaunchAgent readiness

`service start launchd` and `service restart launchd` will wait for the same
facts used by operator health reporting rather than sleeping for a fixed time.
Success requires:

- the expected LaunchAgent is loaded and running;
- a process registry entry exists for the bridge runtime; and
- its runtime health snapshot is fresh and `connected`.

The wait is bounded to 30 seconds and polls at a short interval. The polling
function accepts injected clock/read/wait dependencies so tests use virtual
time and never start a real LaunchAgent.

On timeout, the command fails with the last observed readiness state and the
LaunchAgent log path. It must not print `Started LaunchAgent` or
`Restarted LaunchAgent` before readiness is proven. `service status` remains a
raw launchd status surface and `service stop/uninstall` do not wait for runtime
readiness.

### 2. Terminal task approval cards

Task approval cards will use the repository's existing managed CardKit path so
the callback message id can resolve to a card instance. When a valid decision
is accepted in its creating scope, the card is immediately replaced with a
button-free decision state:

- `execute`: approved and handed to the Agent runtime;
- `modify`: cancelled and waiting for a revised task;
- `cancel`: stopped without execution.

This is the terminal state of the approval decision, not the terminal state of
the Agent task. Agent progress and final output continue through the existing
task delivery path.

Card updates are best-effort carrier work. An update failure is logged and the
existing textual response or task execution continues. A carrier failure must
not reverse, duplicate, or reinterpret an already validated approval decision.
Repeated or cross-scope callbacks remain rejected by the approval store.

### 3. Strict fenced-command normalization

The Feishu intake boundary will unwrap content only when all of these are true:

- the whole trimmed message is one fenced code block;
- the optional fence language is `plain_text`, `plaintext`, or `text`, matched
  case-insensitively;
- the body contains exactly one non-empty line; and
- that line begins with `/`.

The normalized line becomes the message content before built-in command
dispatch and run-policy parsing, so both `/cd`-style built-in commands and
`/visual`-style task directives work.

Messages with surrounding prose, multiple non-empty lines, multiple code
blocks, unsupported language tags, or a body that does not begin with `/`
remain unchanged. This prevents a formatting convenience from becoming a
multi-command execution surface.

## Verification

The implementation will follow TDD with red-green evidence for:

- readiness succeeds only after a fresh connected runtime appears;
- readiness times out with actionable diagnostics and no false success;
- restart retains the installed endpoint configuration;
- execute, modify, and cancel replace approval buttons with the correct
  decision state;
- a failed card update does not block the validated decision;
- one fenced slash command is unwrapped;
- prose, multiple commands, and ordinary code blocks are preserved;
- `/visual` reaches run-policy parsing after normalization.

PR evidence must include:

```text
pnpm public-safety-check
pnpm test
pnpm typecheck
pnpm build
node dist/cli.js architecture check
node dist/cli.js architecture contracts
```

The final state for this iteration is `PR-ready`, not `publishable`. Package
contents, temporary install smoke, registry availability, npm identity, and
owner release acceptance are a later release iteration.

## Non-goals

- Publishing to npm, creating git tags, pushing, or creating a hosted release.
- Running npm pack/install, registry-name, or npm identity checks.
- Adding thread, fork, queue, remote execution, or new Dynamic UI semantics.
- Persisting approval cards or approval decisions across bridge restarts.
- Building a generic service supervisor or generic message-markup parser.
- Changing credentials, npm authentication, repository visibility, or release
  permissions.
